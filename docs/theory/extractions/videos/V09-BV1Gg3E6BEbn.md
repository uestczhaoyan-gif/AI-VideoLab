## 1. 00:00–00:30：从手写提示到自动编排

**V09-C01〔作者表述〕**：自己先构建 vibe-motion 做动画，虽然替代了部分传统工具，但描述动效仍耗时；于是把视觉提示词的撰写也交给 Agent，让视觉导演与动画编码 Agent 交替工作，形成 B-roll 制作流程。

**V09-C02〔研究者解释〕**：自动化的对象不仅是最后的渲染，还包括任务切分、资料／资产准备、提示词生成、代码实现与检查。这个思路可作为 VideoLab 后续“主题 → 分段任务 → 制作 → 检查”的候选组织方式。

## 2. 00:30–01:08：非交互 CLI 与分工

**V09-C03〔作者展示与表述〕**：用 Claude Code 的非交互 `claude -p` 调用子任务，让外层 CLI 执行它，并控制每轮输入和执行。00:54–01:04 明确报告：GPT 5.6 对脚本切割、查资料、找素材，Qwen 3.8 preview 写 React，Remotion 渲染 Motion Graphics。这里是**不同模型按任务分工**，不只是把一个模型分成两个角色。

**V09-C04〔边界与源码补查〕**：后续已取得 P11 的主 Prompt、单镜头脚本与技术测试，但视频拍摄时的准确 commit、真实调用日志、预算和质量审片证据仍缺。当前固定仓库模板用 HyperFrames／HTML，而视频讲 React／Remotion；不能拼成同一版本。脚本调用 Claude Code，也未显式锁定实际模型 ID。“可以 24 小时工作”“没有人工干预”是作者对该案例的声明，不是本项目验证结论。

字幕出现的模型名包括 GPT 5.6、Qwen 3.8 preview；后续比较又出现 GPT 5.5 等名称。按原画面保留，不据此认定当前官方产品名称、可用接口、价格或性能。

## 3. 01:10–02:02：堆 Skill 未必改善表现

**V09-C05〔作者经验〕**：最初 auto-motion 容易产生蓝紫、幻灯片式动画；即使找到大量 art skills，也可能不加载，或结果仍不理想。

作者指出无节制加入 Skill、MCP 和相互矛盾的用户／项目指令会分散注意力。01:50–02:00 以用户级说向北、项目级说向南为例，说明提示约束冲突的问题。

**V09-C06〔研究者解释〕**：对资料库而言，“收集得多”与“每次都加载得多”应分开。可先按用途、风格与执行阶段路由到少量相关文件，避免把所有方法、禁令和工具说明同时放进 Prompt。

## 4. 02:02–02:40：固定模型再评估 harness

**V09-C07〔作者表述与画面〕**：引用其所称 Self-Harness 的定义：固定 LLM 和评价条件，调整周边的上下文、工具与运行编排。02:20 画面同时展示 Model、Evaluator 和 Harness；其论点不只是“装一个 Skill”。

作者以拟物 UI 为例，称 Qwen 3.8 已有较好的掌握，而 GPT 5.5 的阴影容易出问题，因此同一拟物 Skill 可能对两者有不同增益。这是**模型与风格适配的假设**，不是已经取得受控数据的能力排名。

这里有两个层次：生产时可以按任务与风格匹配多个模型；测某条 Skill 的增益时，则固定相应模型与其他条件做 A/B。两者不矛盾。不能把“评测时固定模型”误读成“制片永远只能用一个模型”，也不能反过来不经测试就写死风格选模表。

## 5. 02:38–03:16：A/B 测试与删去冗余规则

**V09-C08〔作者方法〕**：同一任务、固定条件，只改变是否提供 Skill，比较输出，再随模型升级重测；删除模型本身已掌握或没有帮助的部分，把上下文留给真正有效的指导。

**V09-C09〔重要证据边界〕**：02:40 的 A/B 示意画面明确写有 `ILLUSTRATIVE`。其中通过率等数字不能直接当成实测数据。后段提到“Google 怎么做”与评测快照，但当前未获得准确仓库、论文与原始结果，不把机构归属或表内数字写成已验证事实。

## 6. 可整理出的候选流程

```text
固定任务与采用条件
  → 规划／视觉导演生成分段任务和镜头输入
  → 编码 Agent 读取本段所需规则
  → Remotion／其他引擎渲染
  → 独立检查与局部返修
  → 记录费用与结果
  → 对有／无规则的同任务结果做对照
  → 保留有收益的规则，删去冗余或冲突规则
```

这是来源归纳，不是本轮已实现的流水线。以后自动执行还需要实际模型适配、权限与工作目录、超时／预算上限、重试、版本和产物检查。
