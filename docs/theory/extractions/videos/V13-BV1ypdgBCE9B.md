## 1. 00:00–03:30 主张：不是视频模型做的，是网页

**V13-C01〔作者表述＋画面 t00030〕**：作者称把整套视频生成流程"封张成"一个 Skill（趁五一假期），本期讲三件事：01 我的视频到底是怎么做的（为什么是网页，不是视频生成模型）；02 背后 Skill 怎么设计（把流程沉淀成可复用的方法论）；03 走一遍完整实战（从一篇文章 → 一个精美的知识讲解视频）。

**V13-C02〔作者表述〕**：视频效果**不是视频生成模型做的，也没有用 NotebookLM**，本身就是一个网页，"我自己 web coding 出来的网页"。为什么不用视频模型？答案两个字：**可控**——字体、配色、每步停几秒、某一帧要不要出现一个精确的数字，在网页里改几行代码就搞定，比视频模型抽卡稳定得多、成本也更低。NotebookLM 试过，"做不了动画的演示效果，出来的都是静态图"；Remotion 这类框架"反而限制了模型发挥，有时候还不如直接让模型写来得自由"。

**V13-C03〔作者表述＋画面〕**：以一支已发布的技术讲解视频为例（口播称"上期这个视频"，并称它"完全由 AI 生成"、"专门为做这期教程做的演示"——**转写在此处语义含混，无法确定指哪一支，不据此认定本片即自动生成**），输入是 Anthropic 最近发布的一篇文章，输出是一个网页：文章拆成 13 个章节、100 多个细粒度讲解步骤，每步都有完整的视觉演示；底部隐藏进度条（鼠标浮到底部才出现），可任意跳章节/步骤；画面没有页码、没有明显品牌标识，"看起来更像一个视频，而不像网页"。

## 2. 03:30–04:15 Skill 是 Harness 的一次具体实践

**V13-C04〔作者表述〕**：上面的效果可以一步步教给 Agent，也确实都能做出来——"模型本身不缺这些能力"。问题是：**怎么让它每次都做得出来、不同人/不同文章/不同主题都稳定产出、开发效率不靠运气**。直接说"帮我做个视频网页"，它可能做得不错，也可能跑偏：画面和口播对不上、章节和音频不一致、后面的章节风格突然和前面完全不搭。所以需要一套机制来驾驭过程：边界、检查点、自检、修复——**这就是 Harness（驾驭工程）**。

**V13-C05〔作者表述〕**：Skill 本身是"一份给 Agent 看的 [SOP/总提示]"，告诉 Agent 什么时候做什么、做到什么标准、哪些红线不能碰；Agent 加载后按规则干活，不用每次重新复述。作者引用"之前教程"的 Harness 六部分：**上下文管理、工具系统、执行编排、状态和记忆、评估和观测、约束和恢复**，并逐项拆解自己的 Skill。作者同时澄清一个误区：**做 Harness 不是非得从零做一个 Agent**——用一个 Skill 约束 Agent 把一件垂直工作做好，也是在做 Harness。

## 3. 04:15–06:15 执行编排：四阶段 + 两个人工检查点

**V13-C06〔作者表述〕**：从一篇文章到视频被切成**四个阶段**，中间卡了**两个人工检查节点**：

1. **阶段一 · 内容编写**：AI 同时产出两样东西——**口播稿**（决定信息描述方式与整体节奏）和**开发计划**（决定每章做几步、每步屏幕放什么）。
2. **人工检查点一**：Agent 被强制停下。人确认：稿子和开发计划要不要改、用哪套主题、素材怎么准备、后续章节是逐章做还是并行做。
3. **阶段二 · 章节开发**：不是一次做完。**第一章开发完必须人验收**（确认视觉气质与节奏是否对上），为后续章节提供"基准参考"；后续可顺序、也可开多个 Agent 并行；每章写完逐项对照检查清单自检，**全部过关才能交付**。
4. **人工检查点二（音频接口）**：确认是否需要自动合成音频；需要走阶段三，不需要直接跳到阶段四用自己声音录。
5. **阶段三 · 音频合成**：Agent 从口播稿对照网页步骤提取音频合成清单，调用 TTS 把口播稿合成音频。
6. **阶段四 · 录屏**：浏览器打开网页、开启音频自动播放、直接录屏，得到"音频和画面天然对齐"的整片视频。

> 与仓库当前 `web-video-presentation` 的 `(chapter, step)` 游标、协作检查点、`AUDIO.md`/`RECORDING.md` 参考文档结构一致（等级 A，但版本可能已变）。

## 4. 06:15–07:20 上下文管理：按阶段分发文档

**V13-C07〔作者表述＋画面 t00360〕**：整条链路横跨四个阶段、涉及一堆复杂流程，**启动时把所有文档一股脑灌进去会严重稀释模型注意力**（画面：`AGENT · CONTEXT / ATTENTION · DILUTED 12% / SIGNAL / NOISE`，字幕"模型的注意力会被严重的稀释"）。做法是把信息拆成多份文档，**每份只在指定阶段读取**：口播稿规范只在第一阶段读、章节开发指引只在开发阶段读、音频合成文档只在音频流程读。好处是"模型任何时候面前摆的都是它最需要的信息"。

## 5. 07:20–09:30 状态记忆、工具系统、约束与恢复

**V13-C08〔作者表述：状态与记忆〕**：跨多步保持连续性的关键记忆是**开发计划 `Outline.md`**。一个项目十几章、上百步，Agent 写到后面时，前面定过的结构、用户在检查点改过的方向很可能已经不在上下文里；开发计划的作用是把关键决定固定下来，成为开发阶段的持续记忆。开发阶段还会强制 Agent 读两个文件：**口播稿**（负责整体节奏，先讲什么后讲什么，画面跟着口播走）和**原文章**（负责信息密度，画面需要的数据、案例从原文补）。三份文档各有分工，避免"结果对了但画面空了"或"信息很多但节奏乱"。本质上是一种**稳健化的工作记忆**：把关键状态写进文件，需要时再读回来。

**V13-C09〔作者表述：工具系统与多 Agent 隔离〕**：Skill 本身没有特殊工具，核心是让模型用好 Agent 自带的读写工具。开发流程支持**多章节并行**，多个 Agent 同时改一个项目会不会冲突？Skill 设计了严格隔离：每章是**独立文件夹（物理隔离）**、每章有**独立 CSS 前缀**（不会互相撞类名）、**全局设计 token**（字体、颜色、间距走全局变量）保证视觉统一——即使每个 Agent 独立开发，风格也一致，各章互不影响。

**V13-C10〔作者表述：约束与恢复〕**：最常见的出错方式往往不是代码报错，而是**用户觉得不对**（这章节奏太快、这个动画 AI 味太重）。Agent 的本能反应可能是重做整个章节——"重新生成对 Agent 来说成本并不高"，但重做整章会把已经做对的部分也改掉，用户反而更不满意。所以 Skill 里有一条关键原则：**反馈修复的最小切片**——先定位问题在哪一层（节奏、视觉、内容还是代码），然后**只改最小切片**，不重做整章。

## 6. 09:30–10:00 评估与观测：自评失真与独立审查

**V13-C11〔作者表述〕**：这块是作者"画心思最多"的，因为它直接对应 Anthropic 提出的**自评失真**问题——让写代码的 Agent 自己评价写得怎么样，结果大概率是"还不错"。因此设计了非常硬性的自检规则：**每个关键流程完成后必须走"自检→修复→汇报"**，每个阶段都有完整的一套自检规则。最终方案是：用 **Agent Teams 开一个独立的 Reviewer Agent**，给它产出文件加对应清单，让它**从零开始逐项检查**；不支持 Agent Teams 就用 **SubAgent**；最次的兜底是当前 Agent 自己逐项核查，**但也必须严格逐项，不允许目测一遍就放心**。

**V13-C12〔作者表述〕**：把这套设计与 OpenAI／Anthropic 的实践对比，"本质上没有区别，都是搭 Harness"，区别是对方搭工业级运行系统，作者做的是 **Skill 级别的驾驭协议**。

## 7. 10:00–15:45 工具链：Claude Code + MiniMax + CC Switch + tmux

**V13-C13〔作者表述：四件套〕**：整套方案主要用四个工具（画面标题 `ACT 12 · 实战环节 · TOOLS`）：
- **Claude Code**：核心执行 Agent（用 Cursor、Codex 或其他支持 Skill 的 Agent 也可以）。终端 `claude -v` 显示版本号即安装成功。
- **MiniMax（Token Plan）**：作者称"国内正常使用 Claude Code 非常困难，我自己也被封了好几个账号"，现在用国产模型搭配——MiniMax 的 Token Plan 与 Claude Code 适配好；订阅的是 **Plus 极速版**，称"速度快、量大管饱、性价比高，日常开发完全够用"；订阅后生成 API Key。
- **CC Switch**：桌面配置工具，可让 Claude Code、Codex、Gemini CLI 等 Agent 切换为任意自有模型；流程里用它给 Claude Code 配置 MiniMax Token Plan，主模型改成 **MiniMax M2.7**，启用后 `claude` 里确认模型已切换并对话测试。
- **MiniMax CLI**：Token Plan 附带**多模态套餐**（图片、语音、视频），自带**每天 9000 字语音合成额度**，作者称"做两篇文章完全够用"；官方提供 CLI，**不用写一行代码，Agent 直接调用完成语音合成**；用 `mmx` 命令验证安装。

**V13-C14〔作者表述：Skill 安装〕**：最简单的方法是访问 GitHub 地址、下载 `web-video-presentation` 的安装包（zip），解压得到 Skill 目录，在工作目录建 `.claude/skills/` 并粘贴，然后在该目录启动 Claude Code；输入时能智能提示出该 Skill 即配置成功。

**V13-C15〔作者表述：SubAgent vs Agent Teams〕**：Claude Code 支持两种多 Agent 能力：
- **SubAgent**：像"子进程"——主 Agent 把任务分出去，子 Agent 在**完全独立的上下文**里完成，再把结果交回；子 Agent 之间**互相看不到、不会讨论**（画面 t00840：三张 `SUBAGENT — 01/02/03` 卡片，`CONTEXT · ISOLATED / STATE · INDEPENDENT / NO CONTEXT`，字幕"各个子 Agent 之间是互相看不到的"）。适合结果导向任务（并行开发多个章节、一次性检查某块代码），**省 token、容易调度**。
- **Agent Teams**：像"项目小组"——一个组长加几个组员，每个组员独立会话，**可以互相发消息、共享任务列表**。适合需要来回反馈的任务（测试看到字号太小→开发改→测试复查），代价是 **token 开销更高**。
- 作者比喻：SubAgent 像派三个人去三个城市办事后回来汇报；Agent Teams 像把三个人拉进同一间会议室边讨论边改方案。Agent Teams 目前是**实验性功能**，需要在全局配置加环境变量启用。
- **tmux**：开源终端管理器，一个窗口管理多个终端会话；配合 Agent Teams，每个组员出现在不同终端面板，可同时看测试员在哪审核、开发在哪写——作者称这是 Claude Code 官方推荐的使用方式。

## 8. 15:45–22:23 实战：从文章到成片

**V13-C16〔作者表述〕**：演示文章是一篇关于"一封邮件发出后的 600 毫秒"的科普（转写为"一封邮件发出后的600毫秒"）。流程：
1. 终端进入项目目录 → `tmux` 进入 tmux 模式 → 启动 Claude Code，**额外加 `--dangerously-skip-permissions`**（作者称 YOLO/优努模式，跳过所有工具调用的人工确认，"为了演示方便，大家使用注意安全"）。
2. 把原始文章丢给 Claude，让它"使用我们的 Skill 完成第一步"→ 开始写口播稿和开发计划；完成后**创建两个审核 Agent 分别自检**（开了 tmux 所以自动分屏展示）；审核通过后主 Agent 按评审结论修改，再交付最终版本。
3. 本地得到两个文件：**`script.md`**（基于原文改写、更适合视频的口播脚本——句子更短、节奏更快、"听起来像真人在聊天，而不是念文章"）和**开发大纲**（把脚本和原文拆成细粒度章节/步骤，标注每步屏幕上应出现什么信息，把控后续开发节奏、章节边界、每步信息密度）。
4. 第一步完成后**停下来问关键问题**：稿子/开发计划要不要改（AI 味重就调整成自己的讲话风格，改了稿子可让 AI 在下一步同步调整开发计划）；选什么**主题**（Skill 内部定义几套风格主题并按内容推荐，也可自己说明想要风格）；**素材怎么准备**（手动提供还是 AI 自己绘制；例子里所有素材都能 AI 生成）；**开发模式**（三种：默认逐章确认 / 第一章验收后顺序做完 / 第一章验收后用 SubAgent 并行开发）。
5. 开发阶段**先只做第一章**：看页面密度、字号大小、动效节奏、信息呈现是否合理，差距大还能及时调整——"第一章就是后续所有章节的基准"。验收时**亲自在浏览器从头点到尾**，看画面是否舒服、节奏是否顺畅、信息是否太密、有没有明显 AI 味；有问题继续让 Agent 调，没问题再做后续章节。
6. 剩余章节并行：作者经验是**最多同时并行跑三个 Agent 比较合适**；每个 Agent 拿到自己负责的章节大纲、Skill 规范、已有代码作参考，各写各的互不干扰；每章完成后进入自检；作者提醒**一定要选能力比较强的模型**，不然多 Agent 调度很容易出错。全部 Agent 开发并自检完成后才汇报完成。
7. 整体验收：检查空白页、动画卡顿、音画对不上、内容错位——"50 多步的项目，中间某一步出现一些问题很正常"，某步效果不好可让它重改。
8. 音频阶段：用 MiniMax CLI 把口播脚本**批量**合成为音频；合成前先从所有章节抽出**详细口播文本清单**（人扫一遍有无错字漏句）；逐条合成，**遇到速率限制（rate limit）报错会记录失败文件并重试，已生成文件自动跳过，中途中断不用重来**；结果在项目目录按章节/字幕目录组织，每步对应音频文件、文件名与步骤编号一一对应。
9. 录屏阶段，网页提供**三种模式**：默认手动模式（不播音频，自由切换步骤，自己录自己的声音）；URL 加音频参数进入**音频播放模式**（仍手动推进步骤，但每步自动播放音频，自选节奏）；URL 加 `?auto=1` 进入**自动模式**（按下空格，页面按音频节奏自动播放）——作者示范后自选适合方式录制。

**V13-C17〔作者表述＋画面 t01320/t01380〕**：收尾把这件事重新定性：表面是"文章变视频的流程"，本质是一次 **Harness 的具体实践**——模型能力已经很强（Claude Code 写代码、MiniMax 提供稳定推理/生成与语言合成），真正要关注的是"怎样把这些能力稳定地编排起来"；把一次复杂内容生产任务拆成**有流程、有状态、有检查点、有自检、有恢复机制的工程系统**。画面总结（23:00）：`HARNESS · 核心价值：把 模型能力 / 工具能力 / 人的判断 组织成一条稳定可控的生产流程`。

## 对 VideoLab 的借鉴（3–5 条，区分现在能做 / 需要新能力）

1. **现在就能做：把"四阶段 + 两检查点 + 第一章基准"写成 Workflow 契约。** 口播稿与开发大纲同出、第一章验收后才放开并行；工作台已有需求/候选/导出，可先把阶段顺序与门记录进 recipe，不必等执行器。
2. **现在就能做：项目记忆四件套定名。** `brief`（需求+确认）、`script`（口播/文案）、`outline`（章节/步骤/每步画面信息）、`source`（原始资料）；规定每阶段只读哪几份。这是把 V12 的 brief 模板与 V13 的 Outline 记忆合并成同一契约的最短路径。
3. **现在就能做：检查点清单化。** 把"第一章验收看什么"（页面密度、字号、动效节奏、信息呈现、AI 味）与"整体验收看什么"（空白页、卡顿、音画不同步、错位）做成可勾选清单，接进工作台审片页或 CLI 交互；这是自动质检前的人工半自动版。
4. **现在就能做：恢复语义写清楚。** 批量 TTS 的"失败重试 + 已生成跳过 + 中断不重来"是最容易照搬的工程细节，建议作为所有批量生成步骤（TTS、分镜图、渲染分片）的默认要求，并显式记录失败清单。
5. **需要新能力：独立 Reviewer / 多 Agent 编排与隔离。** "独立 Agent 从零审查 + 逐项清单"需要会话编排、额度与产物隔离；建议先实现"脚本硬检查 + 清单人工复核"，再按真实需求接 Agent Teams/SubAgent 级联。
