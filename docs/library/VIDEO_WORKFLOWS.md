# 视频 Workflow 总表（按视频整理，从简到繁）

> 本文件把用户给过的 14 条视频各自整理成一份 **Workflow 总结 / 提示词入口**，按复杂度从 1（最简单）到 5（最复杂）排序。**不删除任何可行方案**：所有条目保留，选择靠“先简单后复杂”，不满意就换下一条或升一档。
>
> 逐条的“本地可执行度”写于三条执行器完成之前，仍是保守结论；新增 `explain-data`（固定数据图表）与 `real-product`（真实截图包装）只覆盖对应子集，不表示已还原各视频的完整 Workflow。
>
> 逐视频的原始证据（时间点、作者表述/可核实事实、读取范围）仍以 [逐来源笔记](../theory/extractions/videos/) 为准；本文件是“选择与执行层”，不替代来源笔记。
>
> 当前有三条本地可半自动执行的 recipe：`code-motion`（文字/图形卡点动效，CLI 可直接生成）、`explain-data`（固定版式数据图解）、`real-product`（真实截图包装）；后两者用 CLI 执行器跑。详见 [recipes/](../../recipes/code-motion/README.md)。下文的“本地可执行度”说明每条视频的流程有多少能落在现有执行器上，**不代表已完整还原该视频**。

## 怎么用

1. **按视频读**：每条视频一节，含一句话、适用场景、步骤、Prompt 可得性、额外资源、覆盖与缺口。
2. **按复杂度选**：先从能满足需求的**最低复杂度**开始；做出来不满意，就换同一档的另一条，或升一档。
3. **记录选择与拒绝理由**：项目里的 `feedback`／`gates` 记录为什么换（内容、风格、节奏、声音、成本），不删旧方案。
4. **升级不是重做一切**：多数升档只增加一个环节（例如从 V10 的展示片升到 V12 的 brief+审片，或从 V06 的选风格升到 V11 的四阶段授权）。

## V03 · GPT6 直出的视频是什么效果

- **复杂度**：1 · 最简单 — 按披露范围只有一个模型、一个既有稿件输入和一句制作指令，没有多工具编排、素材来源、模板或人工确认环节被记录；复杂度只在此披露范围内计为 1。
- **提取状态**：not_extracted — 这是“已有稿件＋宽泛风格要求”的成片展示，作者没有讲制作工作流；公开的只有内容稿、短指令与模型设置，缺 Prompt 原文、宿主与工具、模板、迭代、成本与验收，无法复现，故为 not_extracted。
- **来源**：大吃一顿鲸 / 3:22；[原视频](https://www.bilibili.com/video/BV1E2t26vEVx/)；[逐来源笔记](../theory/extractions/videos/V03-BV1E2t26vEVx.md)
- **一句话**：把作者自己的逐字／录音稿作为内容输入，用页面所称 GPT 6 的极高思考设置、不开极速模式，提出“生成 YouTube 风格口播视频”的短指令，一次得到约 3 分 22 秒的观点讲解成片。
- **本地可执行度**：不适用：成片展示，无公开制作链。

### 适用与输入

- 适用：给定稿件的一次性口播视频生成（作者称“直出”）

## V05 · 用 Agent 做讲解视频：我的 AI 视频制作流程和开源 SOP

- **复杂度**：5 · 最复杂 — 环节最多（规则与设计、静态／动态测试、稿件配音、拆段、生成、分段并行、初审、总装、声音字幕封面、复盘），工具跨 6 种以上（FFmpeg、Remotion、ChatCut、Recordly、ChatGPT 生图、Google Flow 生视频），人工确认节点多，且配音时基锁定使返工代价高、依赖链长。
- **提取状态**：workflow_extracted — 笔记按阶段记录了完整协作图景（人定内容与风格 → Agent 拆解准备 → 人选择生成段并手动生成 → 分段对话执行 → 人审设计与样片 → 总装声音字幕 → 人验收 → 经验沉淀），并给出工具分工、规则三层与限制，足以按流程复现方法；缺的是 Prompt 原文、精确成本与作者工程，属成品级缺口，故为 workflow_extracted。
- **来源**：一只桌子_table / 7:32；[原视频](https://www.bilibili.com/video/BV1xGah67E1j/)；[逐来源笔记](../theory/extractions/videos/V05-BV1xGah67E1j.md)
- **一句话**：先定稿文案与配音，再用 Agent 按配音拆段、准备任务与提示词，人手动生图／生视频并在分段对话中执行，经设计图与样片初审后总装声音字幕封面，最后人工验收并复盘沉淀经验。
- **本地可执行度**：部分：确认门、时基与分段思路可用于项目契约；SOP 细节需人工阅读 P04。

### 适用与输入

- 适用：配音锁时基的分段人机协作讲解视频 SOP
- 输入：已确认的文案与配音（配音可用 AI；作者建议自己读一遍）；字幕；角色 IP 与系列风格方向；参考图与运动参考；项目规则（AGENTS.md）、设计规范（DESIGN.md）、制作 SOP；生成工具与额度（ChatGPT 生图、Google Flow 生视频）；录屏素材（Recordly）与真实素材（如适用）
- 输出：静态／动态设计决定（写入 DESIGN.md）；分段表与各段独立目录、开工提示词；生图／生视频提示词与生成素材；各段成片与几秒样片；总装时间线；SFX／BGM／字幕；封面图与多平台提示词；复盘经验（下一期规则）

### 步骤

1. 建立项目规则：用 AGENTS.md 承担任务路由与常见注意点，例如录屏任务读对应经验、动画记录关键动作时间以便后期音效对点。 工具：AGENTS.md（作者自己的规则，可借鉴或修改）。 产出：项目规则／路由文件。
2. 做静态设计测试：比较背景、字体、角色与整体协调，用参考图帮助表达目标。 工具：静态设计测试（人判断）。 产出：静态设计候选与参考图。
3. 做动态设计测试：关注预备、惯性、跟随、挤压拉伸、次级动作等传统动画原则（示例：方块怎样变成电脑、小球碰撞后对象是否表现出受力关系）；可让 Agent 拆解喜欢的运动参考再实测。 工具：Agent 拆解运动参考 + 动态测试。 产出：动态测试结果。
4. 静态和运动都满意后，把采用方案写进 DESIGN.md；三层分工为：SOP 写制作顺序、项目规则告诉 Agent 当前该读什么经验、DESIGN 记录画面与运动设计。 工具：DESIGN.md + SOP + AGENTS.md。 产出：系列设计规范。
5. 定稿文案并制作配音：作者称文案往往最耗时；配音可用 AI，但建议自己把稿子读一遍；配音与字幕出来后，才进入依赖正式时间的制作。 工具：人工写稿／读稿 + 配音（可用 AI；作者未记录具体工具）。 产出：定稿文案、配音、字幕。
6. 按配音拆制作大段：每段明确声音已经说了什么、画面要补充什么、屏幕真正需要留下什么；只把配音变成飞来飞去的大字仍接近 PPT。 工具：人工 + Agent。 产出：分段表（每段的画面信息增量）。
7. 让 Agent 标出需要人工审查的部分，并推荐适合生成视频的段落，由人选择；推荐不代表自动采用。 工具：Agent。 产出：人工审查清单与生成段建议。
8. Agent 读取作者经验后准备完整的生图／生视频提示词与操作步骤；作者本人在 ChatGPT 的 Chat 界面生图、在 Google Flow 生视频，并按自己的角色 IP 与工具调整。 工具：Agent（准备提示词）+ ChatGPT Chat 生图 + Google Flow 生视频。 产出：生成素材与操作步骤。
9. 人审过分段表后，Agent 为各段准备独立目录与开工提示词；作者按段打开多个对话并行处理，同时手工生成素材。 工具：Agent + 多对话并行 + 分段目录。 产出：各段独立任务目录与开工提示词。
10. 先交设计图与动画标注供初审，避免直接重做整段造成较大 token 消耗；遇到连续状态转换等难点，先做几秒样片；运镜与节奏经验由项目路由加载。 工具：设计图／动画标注 + 几秒样片。 产出：初审通过的段方案／样片。
11. 开场单独打磨：在 Chat 中先让模型提出方案、反思后认真看第二版；满意后整理为可交给执行 Agent 的 MD，不满意则提供具体方向。 工具：Chat 模型 + 人工判断。 产出：开场执行 MD。
12. 分段完成后总装，再处理 SFX、BGM 与字幕；此前保存的动作时间戳用于对齐声音，声音电平范围已有经验参考。 工具：未记录（作者整体使用 FFmpeg、Remotion、ChatCut；总装环节未指明）。 产出：总装时间线与声音字幕。
13. 音乐与音效先让 Agent 提案，作者仍靠听辨决定；字幕由人检查错字与遮挡。 工具：Agent 提案 + 人耳／人眼检查。 产出：采用的声音与字幕。
14. 封面按职责区分：一张控制画风、另一张控制构图，再生成不同平台所需的提示词并手动生图。 工具：生图工具（作者手动操作，具体工具未记录）。 产出：封面图与各平台提示词。
15. 完成一条后让 Agent 梳理哪些环节返工、哪些事项需反复提醒、哪些原先没注意到的问题可优化流程，把经验保存供下一期使用。 工具：Agent 复盘。 产出：经验沉淀（下一期规则）。

### 质量检查

- 参考拆解要补看快闪转场：最短片段阈值可能漏掉快闪；弹幕密度只能辅助定位观众关注处
- 关键静帧由人判断“是否正确表达稿件”，AI 只补运动
- 逐章审阅动效/节奏，最终必须全片带声音检查；技术通过或静帧不等于完整审片
- 独立审查分开审动效、核事实、听声音；看板要确认“指出过”的问题真正关闭
- 修改后的重渲范围与依赖正确：单关键帧→相邻段；旁白/字幕长度→覆盖该句的若干段并重排后续；引擎/后期设置→可能全片失效
- 配乐/音效逐首核许可并署名（视频给出 Lee Rosevere / CC BY 4.0 的例子）
- 成本口径分开：API 标价折算、订阅分摊、人时与硬件渲染；token 统计避免取动画滚动中的中间值
- 不把“150 万播放”等流量数据当作质量或方法有效性的证明

### 坑与限制

- 长稿只在一个对话里来回改会丢上下文；需要外部文件/画布/评论与采用状态
- 复杂数据图与 Three.js 原型若先铺全片会返工；应先拿最难镜头试工具
- 任何修改都重渲整章很慢；要按关键帧拆成小段并管理依赖
- “指出过”不等于问题已修掉；成片后仍可能发现已指出的事实错误而回头重渲
- 配乐方向拖到动画末尾才定会造成打磨时间不足；应在试镜期确定方向
- 逐字时间戳不一定拿得到；作者长片实际是句级对齐，不能写成已逐字同步
- 订阅估算、API 标价与缓存命中不能混算；31:20 画面滚动中的约 14.2 亿 token 不是最终 38.9 亿
- 跨平台曲库不能默认复用许可；独立审查也有成本与失败（审片超时、返工）
- 作者展示的工具/模型分工是个人经验，不是受控能力排名

### 质量检查

- 确定性：同一秒每次画出来都一样（渲染前验证；禁 Math.random / Date.now / rAF / 定时器 / CSS 动画，帧间不保存状态）
- 每个镜头截 3 张静帧自查；关键状态变化与镜头接缝在工作区连续播放检查事件同步与动作承接
- 抽帧拼图 + 手机尺寸 + 文字框景（qa/text.json）+ 按镜头运动/flash frame 报告，自动揪坏帧和看不清的字
- 声音看波形与响度，并量“最重那一下之前有没有真的留出那口气”（DROPS 呼吸）
- 硬指标脚本判 PASS/FAIL：尺寸/帧率/时长/帧数/音轨/黑帧/响度/峰值/循环接缝；一项不过不交付
- 未传规格或未检查项显式 NOT CHECKED，不得默认通过
- 独立审片员只看 QA 材料 +「观众记住的一句话」+ 禁止清单，不回看代码与自审记录
- 人检法：把字幕藏起来看一遍，光看画面还能看懂才算真的在讲（防止翻 PPT）
- 三处确认门：需求/Brief、风格帧、导出前；确认依据记录（谁、何时、基于哪个版本）

### 坑与限制

- 模型发挥不稳定：同一需求跑三次出现「惊艳／翻车／又是老一套」，观众已经能认出是哪个模型做的
- 不加约束时总用同一套套路，单支很炫、刷多了审美疲劳
- 讲解片最常见失败：把口播一句一句做标题卡，再包淡入/背景粒子，“看着在动，其实就是在翻 PPT”
- 模型看不了连续视频、也听不到声音，所以质检必须材料化（图和数字），不能让它“目测”
- 长片不能一口气做完：先关键帧、方向对了再做动画、节奏定下来再渲高清，否则返工大
- 黑盒等待与返工是设计实时预览的直接动机；但预览确认 ≠ 验收，仍需技术检查与人工终审
- 有口播时人说话时配乐与音效必须让开；转场只会弹入弹出、同一时刻让观众看两样东西都会露馅
- 依赖 Node / ffmpeg / Playwright（setup.sh 会装 Chromium），本机未安装、未验证可运行性；43 风格文件全文未取得，仅核对数量与 INDEX 描述
- 成本/耗时未给：只有传统流程对照（知识博主一条视频一整天、App 预览外包几千块，作者说法未核实），不能当项目成本口径
- 模型标签（Opus 5.5、Seedance、p5.brush 等）未核验版本、可用性与价格；与 V13 的 web-video-presentation 不是同一个 Skill，不能混用

### 用户补充（2026-11-09 观看后）

- 不同片子要调用不同工具：网页、SVG、Canvas、WebGL、着色器、Three.js、p5.brush 等；不同风格用不同工具，效果不同。
- 声音都可以由代码算出来，甚至不同乐器；卡点会比剪辑更快更好。
- 想要好视频不能泛泛而谈，要给对标（广告、电影片头等），学节奏/构图/配色思路，不照搬别人的故事、角色、镜头、旋律；可以直接给参考视频让 AI 先拆解。
- 多做三个思路——越先想到的越可能被用烂。视频要有起伏、有高潮有低谷，BGM 跟着变化；有人声时人声优先。
- 好转场是“下一个画面从上一个画面里长出来”；淡入淡出最普通、很像 PPT。2D 动画镜头也可移动。同一时刻只让观众看一样东西。
- 讲解视频不要做成 PPT 演示，哪怕没有讲解也要让人看懂。产品片要让 AI 先读仓库代码并给真实产品界面，演示加光标与反馈。
- 再建一个 Agent 专门挑刺：“作为专业的设计师”，每帧都查看。片子越长越不能一口气做完：先关键帧、再动画、再渲染高清。
- 仓库里有对应 Workflow，把这些技巧写成流程；做之前写 Brief，可快速复用同样风格。

### 步骤

1. 阶段一 内容编写：AI 同时产出两样东西——口播稿（决定信息描述方式与整体节奏，句子更短、节奏更快、“听起来像真人在聊天”）与开发计划/Outline.md（把脚本和原文拆成章节/步骤，标注每步屏幕上应出现什么信息，决定节奏、章节边界与信息密度）；完成后创建两个审核 Agent 分别自检，主 Agent 按评审结论修改 工具：Claude Code + web-video-presentation Skill。 产出：script.md 口播稿 + Outline.md 开发计划（两个审核 Agent 的自检记录）。（依据：视频 C06、C08、C16；仓库当前版本有 (chapter, step) 游标与协作检查点（等级 A，版本可能已变））
2. 人工检查点一（强制停下）：确认稿子/开发计划要不要改（AI 味重可调成自己的讲话风格，改稿后同步调整开发计划）、用哪套主题（Skill 内定义几套并按内容推荐）、素材怎么准备（手动提供或 AI 绘制）、开发模式（默认逐章确认 / 第一章验收后顺序做完 / 第一章验收后用 SubAgent 并行开发） 工具：人工判断 + Skill 内主题与检查点机制。 产出：确认后的稿子/计划/主题/素材策略/开发模式。（依据：视频 C06、C16）
3. 只做第一章并人工逐点验收：亲自在浏览器从头点到尾，看页面密度、字号大小、动效节奏、信息呈现是否合理、有没有明显 AI 味；有问题继续让 Agent 调；第一章就是后续所有章节的视觉/节奏基准 工具：浏览器 + Agent。 产出：第一章基准 + 验收记录。（依据：视频 C06、C16；借鉴清单第 3 条（B 级演示））
4. 后续章节开发：可顺序或最多 3 个 Agent 并行；每章独立文件夹（物理隔离）、独立 CSS 前缀（不撞类名）、全局设计 token（字体/颜色/间距）保证视觉统一；每个 Agent 拿自己负责的章节大纲 + Skill 规范 + 已有代码参考；每章写完逐项对照检查清单自检，全部过关才能交付 工具：SubAgent / Agent Teams + tmux（每个组员一个终端面板）+ Vite+React+TS 模板 + 全局 tokens.css。 产出：各章网页 + 每章自检记录。（依据：视频 C09、C16）
5. 人工检查点二（音频接口）：确认是否需要自动合成音频；需要则走阶段三，不需要直接跳到阶段四用自己声音录 工具：人工判断。 产出：音频方案决策。（依据：视频 C06）
6. 阶段三 音频合成：先从所有章节抽出详细口播文本清单（人扫一遍有无错字漏句），再逐条调用 TTS 合成；遇到 rate limit 记录失败文件并重试，已生成文件自动跳过、中途中断不用重来；结果按章节/步骤组织，文件名与步骤编号一一对应 工具：MiniMax CLI（作者用，称每天 9000 字语音合成额度；未核实）、Skill 的 TTS 脚本（extract-narrations.ts / synthesize-audio.sh / tts-providers/minimax.sh）。 产出：按章节/步骤编号对应的 TTS 音频 + 失败清单。（依据：视频 C06、C13、C16；仓库 TTS 脚本与 AUDIO.md 结构（等级 A，版本可能已变））
7. 阶段四 录屏：网页三种模式——默认手动模式（不播音频、自由切换步骤、自己录声音）；URL 加音频参数进入音频播放模式（仍手动推进、每步自动播放音频）；URL 加 ?auto=1 进入自动模式（按空格后页面按音频节奏自动播放）；浏览器打开网页、开启音频自动播放、直接录屏，音画天然对齐 工具：浏览器录屏 + Skill 的 track 模板/hooks。 产出：录屏成片（音频与画面天然对齐）。（依据：视频 C06、C16；track 模板 hooks（等级 A））
8. 整体验收与最小切片修复：检查空白页、动画卡顿、音画对不上、内容错位等；“50 多步的项目中间某步出问题很正常”；反馈修复先定位问题在哪一层（节奏/视觉/内容/代码），只改最小切片，不重做整章 工具：人工验收 + Agent 定向修复。 产出：整体验收记录 + 修复后的成片。（依据：视频 C10、C16）
9. 贯穿全流程的 Harness 机制：按阶段分发文档（口播稿规范只在阶段一读、章节开发指引只在开发阶段读、音频文档只在音频流程读）；Outline.md 作跨步工作记忆，开发阶段强制回读口播稿与原文；每个关键流程走后“自检→修复→汇报”；最终用独立 Reviewer Agent（Agent Teams）从零逐项检查，不支持则用 SubAgent，最次当前 Agent 严格逐项自查（禁止目测） 工具：Skill 文档分文件 + CHECKLIST + Agent Teams / SubAgent（实验性，需环境变量启用）。 产出：阶段化上下文、持续记忆、自检与独立审查记录。（依据：视频 C07–C11）

### 坑与限制

- 画面与口播对不上、章节与音频不一致、后段风格突变是常见跑偏
- 自评失真：写代码的 Agent 自评大概率“还不错”，所以要有独立审查或强制逐项自检
- Agent 本能重做整章：重生成成本低但会破坏已做对的部分，用户反而更不满意——必须最小切片修复
- 启动时把所有文档一股脑灌入会严重稀释模型注意力（画面量化到 12%），必须按阶段分发
- 多 Agent 并行会撞类名/风格漂移，需要独立文件夹+CSS 前缀+全局 token；且要多 Agent 调度稳定，作者提醒要选能力较强的模型，经验上最多同时并行 3 个
- TTS 会遇 rate limit；不做断点续跑就会重来
- Claude Code 在国内使用困难（作者称被封好几个账号），才用 MiniMax+CC Switch 组合；这些是作者说法，未核实
- --dangerously-skip-permissions 是演示便利，跳过人工确认有风险，不能照抄成默认权限
- 本片是 2026-05 的 web-video-presentation（网页→录屏，节奏由点击/音频推进），与 V12 的 motion-showreel（逐帧时间表）不是同一个 Skill；仓库当前版本 1.2.2 不证明录制时版本
- 21:33–22:20 的“演示音频”整段是影片自身旁白，不是作者讲话（转写陷阱）
- 成本/耗时未给：只有 MiniMax Plus 极速版订阅（价格未提）、每天 9000 字额度、“做两篇文章完全够用”、演示项目 50 多步、上一支 13 章 100 多步；都不能折成项目成本或工期承诺

- **一句话**：把产品宣传片拆成“真实页面/截图 → 镜头卡选择 → Remotion 逐帧动画 → 卡点与音效 → 逐帧检查 → 可编辑 MP4/剪映工程”，让不同 Agent 复用同一套镜头语言。

### 适用与输入

- 适用：真实 Web/桌面产品宣传片；单镜头抽取；已有产品片补音效/换镜头；长视频混用多种镜头风格。
- 输入：真实产品页面/截图/录屏、产品定位与文案、BGM/音效要求、目标时长与画幅。
- 输出：可继续修改的 MP4、动效工作台、剪映工程（作者描述，未运行）。
- 工具：video-shotcraft Skill + Remotion + Node + Puppeteer + 声音设计工具。
- 人工/成本：未记录；仓库大、依赖多，首次安装与渲染时间未知。

### 步骤（按仓库 README/SKILL 归纳，未实测）

1. 判断任务范围：只做已有视频/镜头音效，还是新做完整宣传片；新片再选“直接套 Ink Press 模板 / 自主自由创作 / 共同创作”三种模式之一。
2. 只读检查产品：了解定位、功能、页面视觉、可展示状态与素材风险；不改业务项目、不采集敏感数据。
3. 从 124 张镜头卡里挑镜头，排分镜；每张卡有设计语言说明与 Remotion demo 实现。
4. 用真实页面/截图与文案，按镜头逐帧写 Remotion 动画；按音乐卡点剪辑，加入音效与 BGM。
5. 逐帧检查（作者强调“作为专业设计师”挑刺）；输出 MP4、动效工作台与剪映草稿。
6. 长视频可混用多种镜头风格；镜头卡可单独抽出复用到别的视频。

## 维护规则

- **一视频一 Workflow**：新视频按 Vxx 追加一节；不改写已有来源笔记的读取范围与缺口。
- **只追加、不删除**：失败或不满意的方案标注“不采用 / 被否原因”，方案本身保留，供下次选择。
- **复杂度可修订**：有新的实测后更新 complexity 与理由，并在本节注明修订日期。
- **执行边界分开**：笔记覆盖 ≠ Workflow 可复现 ≠ 本机可执行 ≠ 成片验收。当前三条 recipe 都有本地执行器，但CLI 直接生成仅 `code-motion`。
- 本文件不改写 PROJECT.md 的阶段与排期；阶段状态仍以 [PROJECT.md](../../PROJECT.md) 为准。
